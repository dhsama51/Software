# M5 SW Implementation Plan

## 1. What "SW implementation" means

M5 asks us to reimplement the M4 circuit as software and compare the Verilog
implementation with the software implementation.

Here, "SW" most likely does not mean firmware running on the FPGA board. It
means a normal software program, such as Python, C, C++, JavaScript, or another
general-purpose language, that reproduces the same behavior as the M4 FPGA
circuit.

So Python or C++ is acceptable as long as the program shows the same 8x8 LED
graphics and follows the same game rules.

The important part is not the language itself. The important part is:

- Implement the same M4 rhythm game behavior.
- Display the result as an 8x8 LED-style graphic.
- Explain how the software implementation differs from the Verilog hardware
  implementation.

## 2. Our M4 circuit to reproduce

Our M4 project is a 4-lane rhythm game.

The FPGA version has these rules:

- The 8x8 LED matrix displays falling notes.
- There are four playable lanes.
- The lane order is `LEFT`, `DOWN`, `UP`, `RIGHT`.
- Each beat can spawn at most one note.
- Notes move downward one row per beat.
- The bottom row is the hit line.
- Pressing the matching joystick direction when a note reaches the bottom row
  clears the note and increases the score.
- Missing a note at the bottom row causes game over.
- `JOY_PRESS` restarts the game.
- `L1~L4` display the low 4 bits of the score.
- Note generation uses an LFSR-based pseudo-random sequence.

The software version should reproduce these visible behaviors.

## 3. Selected software language

Python is the best choice for this assignment, and the actual implementation
uses Python with `tkinter`.

Reasons:

- Fast to implement.
- Easy to show an 8x8 LED grid with a small GUI.
- Easy to record or demonstrate.
- Easy to explain in the M5 comparison.
- `tkinter` is included with standard Python, so no extra package installation
  is required.

Implemented file:

- `m5_rhythm.py`

Alternative:

- A `pygame` version is also possible, but `pygame` was not installed in the
  current environment. A terminal version using `curses` or plain text is
  possible, but a GUI is better because the assignment explicitly mentions 8x8
  LED graphics.

## 4. Software architecture

The software should be split into three conceptual parts.

### Game state

Stores the current rhythm game state:

- `lane_left`
- `lane_down`
- `lane_up`
- `lane_right`
- `score`
- `game_over`
- `lfsr`
- `blink_on`

This mirrors the registers in Verilog.

### Update logic

Runs once per beat:

- Check whether a bottom-row note was missed.
- Shift all lane data downward.
- Advance the LFSR.
- Spawn zero or one new note.

This mirrors the clocked `always @(posedge CLOCK_50)` logic.

### Rendering

Draws the current game state as an 8x8 LED matrix:

- Off cell: dark.
- On cell: bright red or green.
- Bottom row may be drawn slightly differently to show the hit line.
- Game over blinks the final state.

This mirrors the FPGA row-scanning output, but the software can draw the whole
8x8 frame at once.

## 5. Input mapping

The PC keyboard should mimic the joystick.

Recommended mapping:

- `Left Arrow`: `JOY_LEFT`
- `Down Arrow`: `JOY_DOWN`
- `Up Arrow`: `JOY_UP`
- `Right Arrow`: `JOY_RIGHT`
- `Space`: `JOY_PRESS` restart

This makes the software version easy to demonstrate on a laptop.

## 6. Pseudo-random behavior

Use the same kind of LFSR as M4:

```text
next_lfsr = {lfsr[6:0], lfsr[7] ^ lfsr[5]}
```

The software version can support two modes:

- Fixed seed mode: useful for comparing with Verilog.
- Runtime seed mode: uses current time or key-press timing, similar to the
  entropy counter added in the FPGA version.

For the final demo, runtime seed mode is more natural.
For comparison analysis, fixed seed mode is easier to explain.

## 7. What to compare in the analysis

### State representation

Verilog:

- State is stored in registers.
- All registers update on clock edges.

Software:

- State is stored in variables or class fields.
- State changes when the event loop calls the update function.

### Timing

Verilog:

- Timing comes from `CLOCK_50` and counters.
- The circuit is always running.

Software:

- Timing comes from the OS timer or game loop.
- Timing can vary slightly depending on the computer and frame rate.

### Parallelism

Verilog:

- Input sync, counters, display scanning, and game logic exist as parallel
  hardware blocks.

Software:

- Logic is executed sequentially inside the main loop.

### Display

Verilog:

- The 8x8 LED matrix is multiplexed one row at a time.
- Persistence of vision makes it look like a full image.

Software:

- The whole 8x8 grid can be drawn at once.
- No electrical row/column scanning is necessary.

### Debugging

Verilog:

- Debugging usually requires recompilation, LED observation, and hardware tests.

Software:

- Debugging is easier with print logs, breakpoints, and visible variables.

### Resource model

Verilog:

- Uses FPGA logic cells, pins, registers, and timing budget.

Software:

- Uses CPU time, memory, and OS-level input/display APIs.

## 9. Expected conclusion

The software version is easier to write, debug, and visualize. The Verilog
version is closer to real hardware: it directly controls GPIO pins, depends on
clock timing, and uses parallel circuit behavior. M5 is meant to show that the
same game logic can be described both as hardware and as software, but the two
implementations think about time, state, and output in very different ways.
